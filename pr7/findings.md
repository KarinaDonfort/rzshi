# Висновки та стан перевірки ПР7

## Реалізація

Застосунок готує та перевіряє зображення, позначає імовірний обрізаний вміст на межі кадру, передає його мультимодальній моделі, перевіряє відповідь за JSON Schema та бізнес-правилами й ухвалює рішення `auto` / `review` / `reject` у коді. Правила охоплюють обовʼязкові поля, IBAN і коди, звірку покупця та постачальника, дати, арифметику позицій і ПДВ. API повертає помилки провайдера як HTTP 502, а не як бізнес-відхилення.

Для одного контрольованого експерименту змінено інструкцію моделі: покупця слід зчитувати з документа, не підставляючи очікувану компанію. Текст усередині документа залишається даними й не змінює програмні рішення.

## Зразки та локальні перевірки

Набір містить 9 чистих, 18 погіршених і 4 власні зразки (разом 31). Власні зразки включають два синтетично погіршені варіанти, фото рахунку №58 з телефона та обрізану версію цього фото. Для всіх зображень внесені еталонні поля в `samples/expected.json`.

- `python -m pytest -q` — **25 passed**.
- Тест правил проходить усі 31 записи еталонних даних з очікуваними рішеннями. Це перевіряє правила на правильних полях, але не доводить точність розпізнавання моделлю.

## Live-оцінювання

Перевірив доступні моделі: `gemini-2.5-flash` відповів 404, а `gemini-flash-lite-latest` успішно прочитав тестове зображення з цифрами `4719`. Перемкнув локальне налаштування `.env` на `gemini-flash-lite-latest`. Після додавання перевірки обрізання та нормалізації порівняння evaluator повторно запущений на 31 файлі; частина викликів усе ще завершилася помилками провайдера:

| Показник | Результат |
|---|---:|
| Файлів у прогоні | 31 |
| Модель | `gemini-flash-lite-latest` |
| Успішно оброблено | 20 |
| Помилки провайдера / runtime failures | 11 |
| Правильні поля в успішних відповідях | 666 |
| Помилкові поля після порівняльної нормалізації | 0 |
| Пропущені / вигадані поля | 0 / 9 |
| Тихі помилки в успішних відповідях | 0 |

Детальний результат збережено в `eval/results-final-guarded.json`. Нормалізація evaluator враховує узгоджені назви типу рахунку, латинсько-кириличні візуальні еквіваленти, десяткову кому/крапку та знак множення в описах. Через 11 runtime failures результат є частковою live-оцінкою. У девʼяти полях модель заповнила значення, яких не було в зображенні; усі ці документи отримали `review`, тож у цьому прогоні жодне таке значення не пройшло тихо в `auto`. Перевірка краю кадру окремо передає фото з обрізаним вмістом на `review`. Результати не підтверджують якість на всіх невдалих запитах.

Після відновлення доступної квоти виконайте новий прогін усіх 31 зразків і збережіть його окремо:

```powershell
python eval/run_eval.py --output eval/results-final.json --compare eval/results.json
```

Перевірте `runtime_failures` перед інтерпретацією метрик. Якщо там не нуль, це часткове оцінювання, а не підтвердження якості моделі.

## Спостереження та обмеження

- Відсутні суми на обрізаних документах мають бути `null`; бізнес-правила передають такі рахунки на `review`. Відсутній необовʼязковий строк дії сам по собі не блокує `auto`.
- Неправильна арифметика рядка в `rahunok-05` і змінений IBAN у `rahunok-06` мають спричинити перевірку людиною, а не автоматичне виправлення значень моделлю.
- Інший покупець та підміна банківських реквізитів у контрольних документах перевіряються правилами покупця й довідника.
- Початкові 49 «тихих помилок» значною мірою були різницею у візуально еквівалентних латинських/кириличних літерах, десятковій комі/крапці та типі документа. Після обмеженої нормалізації цих еквівалентів у новому прогоні немає тихих помилок; вигадані значення отримали рішення `review`.
- Поріг мінімального розміру зображення — евристика, а не виміряна межа читабельності. Для визначення практичної межі потрібні безпомилкові live-прогони на різних рівнях якості.

## Підсумок

Кодова частина, еталонний набір, власні зразки та локальні тести готові. Нові перевірки пройшли тести; останній live-прогін обробив 20 із 31 файлів, 11 запитів не пройшли через помилки провайдера. На успішних відповідях девʼять вигаданих полів були направлені на ручну перевірку, без зафіксованих тихих помилок. Після поновлення квоти потрібно повторити прогін для повного кількісного висновку.
